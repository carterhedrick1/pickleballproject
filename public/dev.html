The Rules We Build By

The current guardrails established while building and operating IN or OUT. These cover how changes ship, how the app should look, and the safety promises future work must preserve.

41 Current Rules
This is a living reference. When a standing rule changes, update this tab and its repository source together so the written rule and the actual workflow stay aligned.

Building And Shipping

8 Rules
  1. 01
    Prove Every Change As A User

    Run the app locally and exercise the affected page, control, or full flow. Passing unit tests alone is not enough for a user-facing change.

  2. 02
    Run The Checks That Cover The Change

    Use the relevant verification scripts, and always pass npm run verify:deploy before a completed change is committed.

  3. 03
    Use Port 3002 For The Local App

    Port 3001 belongs to another project. Resolve the listener on exactly 3002 and never stop an unidentified Node process.

  4. 04
    Restart After A Completed App Update

    Stop only the IN or OUT process on port 3002, start PORT=3002 npm start, and confirm the local health endpoint and changed behavior.

  5. 05
    Commit Completed Changes On Main

    Unless Scott says otherwise, a finished app change is committed. The post-commit workflow verifies it and pushes both repository remotes.

  6. 06
    Treat The Upstream Push As The Deploy

    Production builds automatically from the upstream main branch. Never push unfinished or unverified work there.

  7. 07
    Verify The New Production Process

    Wait for a new server start time, check production health, and exercise the affected behavior on inorout.club before calling the work complete.

  8. 08
    Use The Manual Deploy Hook Only As A Fallback

    Use it only when the automatic deployment did not start, failed, stayed on the previous version, or Scott asks for an additional restart.

Documentation And The Developer Area

5 Rules
  1. 09
    Refresh Screens After Every Visible Change

    Run npm run docs whenever copy, styles, layout, controls, screens, or user flows change.

  2. 10
    Photograph Every Changed State

    If the Screens gallery does not already cover the changed state, add it to scripts/capture-screens.js.

  3. 11
    Publish And Check Screens Locally And Live

    Publish locally before the commit and verify through Developer Area → Screens. After deployment, publish production and confirm the new timestamp and gallery.

  4. 12
    Leave The Old Artifact Copies Alone

    The Developer Area copies are the maintained reference. Do not republish the older external artifact pages unless Scott asks.

  5. 13
    Keep The Developer Area Private And Useful

    Leave it unlisted and password protected. Keep shipped ideas current, and keep the global error reporter fail-silent so reporting can never break a player page.

Interface And Content

9 Rules
  1. 14
    Capitalize Every Word In Authored UI Titles

    Titles, headings, tabs, short labels, card titles, option titles, and button labels capitalize every word, including short words.

  2. 15
    Preserve Intentional Product And Acronym Casing

    Keep SMS, DUPR, and API as acronyms, and preserve the product styling “IN or OUT” or “In or Out.”

  3. 16
    Keep Explanatory Copy In Normal Sentence Case

    Help text, full sentences, placeholders, and user-provided content should read naturally rather than use title capitalization.

  4. 17
    Use Only The Six Court Classic Base Colors

    Brand, Ink, Canvas, Surface, Warning, and Danger are the base palette. Derive every other tone through opacity or color mixing.

  5. 18
    Give Every Color One Job

    Brand means action, selection, focus, or success; Warning means attention; Danger is reserved for destructive actions and errors.

  6. 19
    Keep A Clear Button Hierarchy

    Use one primary action per section. Secondary supports, Danger destroys, and Quiet goes back, cancels, or dismisses.

  7. 20
    Use Only Three Button Sizes

    Compact is 36 px on dense desktop rows, Standard is 44 px, and Large is 52 px. Compact controls become at least 44 px on small screens.

  8. 21
    Make Forms And Focus Consistent

    Controls share heights, radii, visible labels, error treatment, and an obvious keyboard focus state.

  9. 22
    Keep Status Color Small And Meaningful

    Use concise messages, badges, icons, or borders. Large panels remain neutral instead of being filled with status color.

Architecture, Data, And Privacy

6 Rules
  1. 23
    Keep The App Login-Free For Players And Hosts

    IN or OUT is a lightweight tool for friends. Public game links and private host management links replace user accounts.

  2. 24
    Keep Local And Production Data Separate

    Local development uses SQLite. Production uses PostgreSQL. Fixture scripts must refuse to create or delete data when that boundary is uncertain.

  3. 25
    Never Expose The Host Token Publicly

    The public game endpoint and player pages must not reveal the private credential that controls a game.

  4. 26
    Keep Host Notes And Roster Details Private

    Host notes, host-entered names, and DUPR details belong to the host and must not appear on player-facing pages.

  5. 27
    Require Host Authorization For Destructive And Media Actions

    Uploading, selecting, clearing, or deleting images—and changing protected game data—requires the correct host credential.

  6. 28
    Remember The Single-Process Lock Boundary

    The per-game lock is safe only while production runs one Node instance. Scaling out requires moving write ordering into the database first.

Automated Test Safety

7 Rules
  1. 29
    Never Send A Real Text From An Automated Test

    Use players without phone numbers whenever possible, and blank the Textbelt key for every test or capture that needs phone numbers.

  2. 30
    Double-Guard SMS Failure Tests

    Use both simulated failure and a blank Textbelt key, and never point the SMS failure verification scripts at production.

  3. 31
    Run Screenshot Fixtures Only On Local SQLite

    The documentation server must reject a production database, use a free port, use reserved 555 numbers, and keep SMS in development mode.

  4. 32
    Clean Up Fixtures Even When A Capture Fails

    Fixture teardown must run after partial failures and match both a marker and reserved phone numbers so it cannot remove a real game.

  5. 33
    Space Out Production Verification Runs

    Run production integration checks one at a time. Production rate limits can turn a safe burst into misleading 429 responses.

  6. 34
    Make Production Cleanup Narrow And Reversible

    Start with a dry run, refuse candidates with phone numbers or reminder history, and write a timestamped backup before deleting anything.

  7. 35
    Trust Verified Behavior Over Old Notes

    Historical project notes are context, not proof. Check the current code, tests, and live system before relying on a claim.

Core Behavior Safeguards

6 Rules
  1. 36
    Never Lose, Duplicate, Or Overbook A Player

    Concurrent actions must preserve every signup, keep the confirmed roster within capacity, and never place one person on both the roster and waitlist.

  2. 37
    Keep Promotion Rules Consistent

    First-come games may automatically promote the next waitlisted player. Approval games leave that decision to the host.

  3. 38
    Send Each Reminder Once, Including Catch-Ups

    Missed reminders can catch up before game time, late joiners still get theirs, and restarts or overlapping checks must not create duplicates.

  4. 39
    Save The User Action Even If Its Text Fails

    A failed confirmation must not erase a signup or cancellation. Retry a transient failure once, do not retry permanent errors, and tell the user the truth.

  5. 40
    Make Cancellation Idempotent

    A cancellation removes only the intended player. Repeating the same cancellation must not remove somebody else.

  6. 41
    Trust Image Bytes, Not File Claims

    Validate uploaded image types from their magic bytes, preserve exact bytes through storage, enforce limits, and keep upload and deletion host-only.

Court Classic Design System

This is the selected visual direction for IN or OUT. Every interface uses these six base colors and the same component rules at every screen size.

Six Base Colors, Each With One Job

Everything else is derived through opacity or color mixing, not another named color.

Brand#166534

Primary actions, links, selection, focus, and success.

Ink#172033

Headings, body text, secondary buttons, and derived borders.

Canvas#F4F6F3

The quiet background behind every page and major section.

Surface#FFFFFF

Cards, forms, navigation, menus, and dialogs.

Warning#A85D00

Waitlists, cautions, and items that need attention.

Danger#B42318

Removal, cancellation, destructive actions, and errors.
